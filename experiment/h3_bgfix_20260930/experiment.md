### 立项依据

诊断（详见 `_test2_extract/` 与 `.workbuddy/memory/2026-09-30.md`）三条硬结论：

1. **不是架构问题**：MiT-B3 与 Swin-L 在 `test_2` 上逐图背景占比相关系数 **0.876**，
   预测类别占比几乎重合（背景 33.94% vs 34.19%，植被 20.94% vs 21.90%）。
2. **是"背景吸引子"式连续塌陷**：按背景占比分桶后其余各类**单调衰减**
   （道路 10.09→0.44、建筑 24.57→2.31、植被 32.27→2.13）。用户观察到的
   "道路、建筑变背景"只是最显眼的症状。
3. **是子群体级分布外**：逐图背景占比中位数 0.26–0.27（与训练先验一致），
   但 `>0.6` 有 222 张、`>0.8` 有 100 张、最大 1.000。塌陷子集图像显著更暗、
   青绿偏色（G−R 由 +1.4 变 +8.3）、暗像素 19%→32%、细节尺度 6.09→3.68。

由此确定改造方向：**不做全局背景降权**（Background 是真实兜底类，训练真值已核对），
改用只在 `GT≠1` 处生效的定向惩罚；并把增强缺少的"降采样/GSD"与"光度域"两个轴补上。

### 本地自检发现并修掉的一个真实缺陷

冒烟测试第一轮 4 项 FAIL，其中 3 项是测试自身预期写错（已修正，详见下），
**1 项是真缺陷**：定向色偏增强**到不了实测幅度** —— 初版手选方向 `(0.30,0.20,0.05)`
配 `cast_strength=0.55`，最强只能把 G−R 推到约 7.2，而实测需要 +6.9 的增量、
要求更强。改为从实测反推方向 `(1-81.4/106.3, 1-89.7/107.8, 1-91.3/100.2)`
`= (0.2342, 0.1679, 0.0888)`，并把 `cast_strength` 提到 1.0 —— 这样 amount=1.0
恰好复现实测偏色、更小的 amount 向内插值回训练观感，增强的幅度范围与测量对齐，
而不是拍脑袋。同时把该断言改成"满强度增益必须复现实测相对亏缺（atol=0.02）"这种
可证伪的形式。

另外 3 项测试预期错误（代码本身正确，记录备查）：

- `F.cross_entropy` 的 `weight` 按**目标类**加权，不是按预测类。所以提高背景权重只对
  **标注为背景**的像素生效；原测试用"全前景标签"的 batch 去验它，必然不动。
  已改为"背景标签 batch 上加权后 loss 变大 + 全前景 batch 上背景权重完全惰性"两条。
- 混淆矩阵 union 应为 `列和 + 行和 − 交集`；原测试漏了行和，算出 0.3667，正确值 0.3250。
- 全零 logits 的 `argmax` 是类别 0 而不是 1，所以"有效标签被预测为 0"应落在 `matrix[3,0]`。
  这一条顺带验证了 H3 文档约定的计分规则：**真实有效而预测为 0 仍算错误**。

#### 启动方式

`baseline` 先单独起（参考臂，时序干净），随后用带槽位限制的并行调度器起其余三臂：

```bash

    20000 1000 2 loss aug full > runs/mask2former_uav/h3_bgfix_screen.nohup.log 2>&1 &
```

槽位取 2（连同 `baseline` 共 3 个进程）。**并发是为了省显存风险，不是为了提速** ——
下表是实测结论：

| 情形 | 每进程 `sec_per_update` | 聚合吞吐 |
| --- | --- | --- |
| 单进程独占 | 0.194 | **5.15 updates/s** |
| 三进程并发 | 0.623 | **4.82 updates/s** |

单进程就已把 GPU 吃到 96%，所以**并发只换来 94% 的聚合吞吐，等于不加速**。
四臂总计 80k update，物理下限就是 `80000 / 5.15 ≈ 4.3 h` 纯训练，再加验证。
这条结论已写回 `screen_parallel_h3_bgfix.sh` 的注释（原注释误称"多槽位能换到真实时间"）。
槽位限制的真正意义是：每进程约 5.2 GB，四个并发只剩不到 4 GB 余量，
一次激活尖峰会把**所有**臂一起打挂。实测三进程占 15.67 GB / 24.56 GB。

四臂的批次顺序与增强序列由种子决定、不依赖墙钟时间，所以并发不破坏可比性。

**ETA**：剩余 73.9k update 训练 + 四臂各 20 次验证（约 60 s/次），
预计约 **5.5–6 h** 完成（起算 11:50）。

#### 运行中发现的问题（11:35 快照）

**1. 三臂都没有代理曲线（不止 baseline/loss）。** 实测三臂 `val_history.jsonl` 的键都只有
`['iter', 'selection_score', 'val']`，`proxy` 整段缺失。根因在 `train_h3_bgfix.py:304`：

```python
proxy_datasets = {...} if args.proxy_weight > 0 else {}
```

代理集**只在 `proxy_weight > 0` 时才构建**。preset 定义（`:58-61`）里只有 `full` 是
`proxy_weight=0.30`，`baseline`/`loss`/`aug` 全是 `0.0`，所以只有 `full` 会出于选点需要
跑代理评估。这不是评估侧漏改 —— 是**我先前对此的判断错了**：我原以为"让代理评估在所有
preset 下生效"已经改到位，实际上它一直是按 `proxy_weight` 门控的，而三臂的 `proxy_weight`
保持 0 是**刻意的**（`aug` 臂若带代理选点，就与 `loss` 臂只差增强这一个变量了，归因才干净）。

代价是：代理曲线只能事后补。补救不需要碰正在运行的任何文件 ——
`eval_proxy.py` 是独立的检查点评估器，跑完后直接

```bash
python experiment/h3_bgfix_20260930/eval_proxy.py \
  --checkpoint runs/mask2former_uav/h3_bgfix_baseline_20k_seed3407/best.pt \
  --checkpoint runs/mask2former_uav/h3_bgfix_loss_20k_seed3407/best.pt \
  --checkpoint runs/mask2former_uav/h3_bgfix_aug_20k_seed3407/best.pt \
  --max-images 200
```

即可把三臂的代理点补齐（脚本自带 `--proxy-scales 0.5,0.625,0.75`，与训练内一致）。
**不在训练中途改代码**：`train_h3_bgfix.py` 虽已被在跑的进程载入内存，
但改动会让后续 `full` 臂与实际跑完的三臂之间存在代码版本差异，破坏可比性。
代价仅是三臂只有"最终检查点"一个代理点，没有代理随训练的曲线 —— 对短预算筛选足够，
全预算那轮应当把 `--proxy-weight` 设小正数（如 0.05）以拿到曲线。

**2. 检查点瘦身生效。** `baseline` 目录 1511 MB ≈ 2 × 0.74 GiB（best + last），

**一个必须踩住的建模陷阱**：`full` 的启动时间取决于**调度器**腾出的槽位，
而调度器只管它自己启动的 `loss`/`aug`/`full`。`baseline` 是单独起的参考臂，

会把 `full` 的完成时间少算一小时。`eta_screen.py` 用槽位队列模拟这一点，
并在检测到非调度器管理的臂时显式提示。

**两点保守之处**：一是 0.78–0.79 是**三进程并发**下测的，`baseline` 14:47 退出后只剩两进程，
`loss`/`aug` 会变快（实测单进程 0.194、双进程约 0.3–0.4），所以 15:43/15:46 是上界；
二是 `full` 的 0.25 s/update 是**模型假设**（单进程 0.194 训练 + 约 0.06 的验证摊薄），
不是实测。综合看，**四臂全部跑完大约在 16:40–17:10**，
比 11:35 快照时按"5.5–6 h"外推的 17:45 略早。

工具：新增 `eta_screen.py`（读本地快照测速率 + 向服务器取当前 iter 与服务器时钟，
槽位队列模拟排队臂）。速率用快照差分得到，本机与服务器时钟的固定偏差会被差分消掉。

#### 12:53 守候改为服务器侧

本地 `watch_screen.py` 已关闭。理由很直接：训练在服务器上是脱离的，但守候脚本在笔记本上，
**关掉笔记本（或这个会话）进度记录就断了**。改为在服务器上记：

```bash
nohup bash experiment/h3_bgfix_20260930/watch_remote.sh 20k 300 baseline loss aug full \
    >/dev/null 2>&1 &
# 日志：runs/mask2former_uav/h3_bgfix_watch.log
```

三个设计要点：

1. **行格式与本地 `watch_screen.py` 逐字一致**，所以下载回来的那份可以直接喂给
   `eta_screen.py --log` 与同一套解析器，不必为两种来源写两套解析。
2. **历史接续**：本地已落的 15 条快照（11:34–12:44）先追加进服务器日志再启动守候，
   下载下来是一份连续记录，而不是从 12:53 重新开始。
3. **自己会退出**：每臂都写出 `exit_code` 后落一行 `all arms settled` 并结束，
   不会永久挂着；`flock` 保证不会有两个实例往同一份日志里交错写。

**服务器上本没有 `watch_remote.sh`，而调度器正在运行，所以不能 `sync`**（bash 边读边执行，

`put`（传单个文件）与 `collect`（一次性回收全部日志与指标）。

`watch_remote.sh` 上线前用桩件测了三条分支：未完成时持续循环、全部落定后自行退出、
失败臂记为 `failed(9)` 而非 `done`。测试环境没有 `flock`，顺带暴露一个真实缺陷 ——
原写法 `exec 9>"$lock"; flock -n 9` 在无 `flock` 的机器上**守卫本身失败即退出**，
表现为"什么都没写就结束"，看起来和跑完一模一样。已改成无 `flock` 时降级并显式告警。
