这条断崖不在数据里，是模型行为。** 同时也要注意：模型**见过**「低细节 + 前景」的配对

**四条判定：**

1. **「低分辨率 / 低细节」这一半成立**，而且是最强的单一相关量（best132k ρ=−0.494）。
2. **「低对比度」这一半不成立**。全局对比度 `contrast_std` 相关极弱（−0.133），
   相对对比度 `contrast_rms` 甚至**反号**（+0.203）——越"相对平坦"的图反而背景更少。
   **别把对比度和细节尺度混为一谈**，需要处理的是高频能量，不是灰度动态范围。
3. **塌陷是「断崖」而不是「斜坡」**：Q1→Q2 从 0.719 掉到 0.317（2.3×），

   **模型在最低细节带的行为偏离了数据先验近 2 倍** —— 这一部分是真实的病理，不是任务上限。
4. **训练先验里没有这条断崖，且模型见过配对**：训练集最低细节箱的**真值**是
   0.391 背景 / 0.609 前景，即「低细节 + 大量前景」的样本有 1120 张。
   模型见过它们，却仍在低细节 OOD 图上塌陷 ⇒ **不是「样本没覆盖到」，而是弱证据时
   背景/no-object 类默认胜出**。这决定了增强（哪怕有针对性的）期望值都不高。
5. **越训越重**：Q1 上 20k 0.636 → 82k 0.676 → 132k 0.719（单调上行），
   与 8 节里「test_2 背景占比 82k 0.3479 → 132k 0.3649」同向。
   **迭代次数不是这个病的解。**

### B2. 归因：「低细节」是病因，还是「外观偏移」的替身？

新增 `attribute_detail_vs_appearance.py`（给 test_2 每张图补算逐通道均值 / 亮度 / 色偏）。
**这一步推翻了上面「细节尺度是主因」的初步归因。**

**原始相关（test_2 1300 张，h2 best132k）**

| 自变量 | `pred_bg` 的 Spearman |
| --- | --- |
| detail_lap | −0.494 |
| detail_hf | −0.439 |
| **cast_br（B−R，蓝偏）** | **+0.437** |
| mean_r | −0.384 |
| lum | −0.357 |
| cast_gr（G−R） | +0.290 |
| contrast_std | −0.133 |

**自变量之间高度共线**

| 关系 | rho |
| --- | --- |
| detail_lap ~ cast_br | **−0.675** |
| detail_lap ~ mean_r | +0.623 |
| detail_lap ~ lum | +0.578 |
| detail_lap ~ contrast_std | +0.522 |

⇒ **「低细节」和「暗 + 蓝绿偏色」几乎是同一个变量**（−0.675），
不是两个独立现象。用户在图上看到的"糊、平"，很大程度就是雾化/低照度/偏色造成的。

**偏相关（谁更直接）**

| 偏相关 | 值 |
| --- | --- |
| `pred_bg ~ detail_lap` ｜ 控 cast_br, lum | **−0.266** |
| `pred_bg ~ cast_br` ｜ 控 detail_lap, lum | +0.141 |
| `pred_bg ~ lum` ｜ 控 cast_br, detail_lap | −0.062 |

⇒ 控住外观后细节仍有独立效应，反之弱得多 ⇒ **细节是更直接的量，偏色主要通过交互起作用。**

**分层（先按蓝偏三档，档内再按细节二分；预测背景占比）**

| 档 | 细节低 | 细节高 | 差 |
| --- | --- | --- | --- |
| 蓝偏低 | 0.305 (n=217) | 0.205 (n=216) | +0.100 |
| 蓝偏中 | 0.350 (n=217) | 0.280 (n=217) | +0.070 |
| **蓝偏高** | **0.759 (n=217)** | 0.289 (n=216) | **+0.470** |

**这是本次分析最重要的一条：塌陷只发生在「高蓝偏 × 低细节」这一个格子里。**
- 单纯低细节（蓝偏低档）→ 0.305，只是轻微偏高；
- 单纯高蓝偏但细节丰富 → 0.289，**完全正常**；
- **两者同时出现 → 0.759，跳到 2.5 倍。**

⇒ **病因不是二者之一，是它们的交互**（对应真值先验 0.28–0.38 的水平，
这一格超出约 2 倍）。


### C. 「训练中随机降低对比度和分辨率」——这个实验已经做过（h3_bgfix `aug` 臂）

`experiment/h3_bgfix_20260930/bgfix_dataset.py` 正是这套改造：

- `zoom_out`：真实降尺度分支（缩到不足 crop 时整图贴进 canvas，而不是被 `max(size,…)` clamp 回去）；
- **`gsd`：最终 patch 先降采样再升采样**，模拟更高飞行高度、标签不动 ← 「随机降低分辨率」；
- **`photometric`：方向性偏色（训练 R/G/B 106.3/107.8/100.2 vs 塌陷子集 81.4/89.7/91.3，
  方向由数据推出而非手挑）+ 白平衡 + 曝光 + gamma + 雾化低对比度 + 噪声** ← 「随机降低对比度」；
- 外加 `GaussianBlur(0.4–1.4, p=0.30)`。

20k、同种子、同协议的四臂结果：

| 臂 | 原生 val mIoU | 代理均值(0.5/0.625/0.75 降采样) | test_2 背景占比 | test_2 `bg>0.8` 图数 |
| --- | --- | --- | --- | --- |
| baseline | 0.7038 | 0.6933 | 0.3087 | 122 |
| **aug（降尺度+模糊+低对比+噪声）** | **0.7042 (+0.05pt)** | **0.6939 (+0.06pt)** | **0.2992** | **101** |
| loss (`false_bg_weight` 0.25) | 0.6863 (−1.75pt) | 0.6780 | 0.2512 | 42 |
| full (0.25+aug+代理) | 0.6837 (−2.01pt) | 0.6758 | 0.2348 | 27 |

**判定：这套增强在域内与代理轴上都只是噪声级收益（+0.05 / +0.06pt，种子噪声 ±0.2–0.3pt），
但在 `test_2` 上把背景占比 0.3087 → 0.2992、`bg>0.8` 图数 122 → 101。
它是四臂里唯一「没有引入新病理」的改造（无碎裂增量，Δbg 流向小）。**

对比之下，真正把 `bg>0.8` 从 122 打到 42/27 的是 **`false_background` 惩罚——一个损失/决策层
的改动**，而它的代价是域内 −1.12 ~ −2.01pt（假阴性 +4.08 ~ +7.75pt）。
**即：域内质量与域外塌陷之间的权衡是硬的，而增强只挪动了很小一段。**

**⚠️ 结合 B2 的交互结论，aug 臂的收益很可能被它的代理指标低估了。**
`eval_proxy.py` 的代理只扫**细节轴**（0.5 / 0.625 / 0.75 降采样），
而病因是「高蓝偏 × 低细节」的交互 —— 单扫细节轴等于只测了交互的一半，
自然测不出收益。而 `aug` 臂的 `photometric` 分支**恰好同时提供了另一半**
（雾化压低局部细节 + 方向性偏色），也就是说 **`aug` 是这批臂里唯一在正确方向上做事的**。
**若要复现这类实验，代理指标必须同时扫「细节 × 色偏/曝光」两个轴，否则会系统性低估。**

### D. 机制修正（原「朴素随机降质无效」的判断需要收窄）

真值侧 `detail_lap ~ bg_frac` 的 ρ = −0.256（有标注）/ −0.265（训练 5598 张），
即**低细节 ⇔ 背景多**。所以「随机给一张图降对比度 / 降分辨率」主要是在合成
（低细节, 背景标签）这种配对 —— 而「低细节 ⇒ 默认背景」正是要拆掉的那条捷径。
**无差别随机降质主要给捷径喂样本，不是拆它。**

**更强的反证**：训练集最低细节箱本身就有 1120 张图、真值 60.9% 是前景。
模型已经见过大量「低细节 + 前景」样本，仍然在低细节 OOD 图上塌陷到 0.719 背景。
⇒ **「低细节图缺少前景监督样本」这个解释不成立**，病因在
**弱证据时 no-object / 背景类的默认胜出**，以及 test_2 低细节子集同时带有
更强的外观偏移（偏暗、蓝绿偏色，见 `bgfix_dataset.py` 里量出的
训练 R/G/B 106.3/107.8/100.2 vs 塌陷子集 81.4/89.7/91.3）。
`attribute_detail_vs_appearance.py` 就是为判别「细节是病因还是外观偏移替身」而写的。

### E. 落地建议

**H2 的 MMSeg 管线里已经有的（别重复做）：**

- 分辨率：`RandomResize(scale=1024, ratio_range=(0.5,1.5), keep_ratio)` + `RandomCrop(512)`
  —— ratio=0.5 时 1024→512、crop 512 即整幅下采样 2× 的画面，**真实降尺度分支存在**
  （这点与 H3 自研那套不同，那套被 `max(size, …)` clamp 掉，模型从没见过 zoom-out）。
- 对比度：`PhotoMetricDistortion` 默认 `contrast_range=(0.5,1.5)`，**±50% 对比度抖动已有**。

**缺的（按 B2 的交互结论排优先级）：**

| 缺的增强 | 对应病因的哪一半 | 优先级 |
| --- | --- | --- |
| 雾化 / 方向性偏色 / 曝光 / gamma | **「高蓝偏」那一半** | **高** |
| 模糊 | 与雾化共同压低局部细节 | 中 |
| down-up 重采样（gsd） | 「低细节」那一半 —— 但 H2 已有 0.5× 降尺度分支 | **低** |
| 噪声 | 未验证 | 低 |

**关键修正：单独加「降分辨率」是打空的那一半。** 分层表里「蓝偏高 × 细节高」这一格
预测背景只有 0.289（正常），说明**只把图变糊、不改变颜色/曝光分布，不会触发塌陷**，
也就不会让模型学会处理它。反过来，「蓝偏低 × 细节低」只到 0.305，也不严重。
**必须同时压细节和改外观，才落在病因那一格。**

若仍要试，建议：

1. 20k 短臂、同种子，对照 baseline，**同时**施加「高斯模糊 + 降采样重采样 + 雾化 +
   数据推出的方向性偏色/曝光偏移」——即 `bgfix_dataset.py` 的 aug 配方（已经验证过方向正确）；
2. **预注册判据必须换掉代理指标**：不要只用单扫细节轴的 `eval_proxy.py`，
   要构造「细节 × 色偏」二维网格的代理集，否则会像 aug 臂那样被系统性低估；
   主判据仍是 `test_2` 的 `bg>0.8` 图数与背景占比，辅助判据是原生 val mIoU（不得低于 −0.2pt）；
3. 期望值上限参考 aug 臂：**背景占比 −1pt 左右、`bg>0.8` 图数 −20 张左右、域内不掉点**。
   想指望它修好坏图，需要更大的改动（决策层）。

**优先级排序（按已有证据的杠杆大小）：**

1. 决策层（塌陷的直接解）：`bg>0.8` 图数 122 → 27/42，但需接受域内代价并做门控
   （只对 `p_bg>0.5` 惩罚，`h3_bgfix` 已论证）；
2. 选点策略：H2 160k 臂应用**末点**而非 best-by-val（test.txt +0.88）；
3. 数据增强：杠杆最小，**且必须是「细节 × 外观」双轴成套的增强**，
   单加降分辨率或单加偏色都会打空。

### 陷阱：`param_schedulers` 会把旧 `end` 一起恢复

结论来自本地 mmengine 0.10.7 源码（wheel 解包逐行读，不是推测）：

| 事实 | 依据 |
| --- | --- |
| `--resume` 不带路径，只能从 `<work_dir>/last_checkpoint` 指针取 | `tools/train.py:19` `action='store_true'`；`checkpoint.py:807` 读指针文件 |
| 指定文件必须 `load_from` + `resume=True` | `runner.py:1686-1693`：`resume and load_from is not None` → 用该路径 |
| `max_iters` **不会**被 checkpoint 覆盖，`iter` 从 `meta['iter']` 恢复 | `runner.py:2022-2023`，且 `save_checkpoint` 不写 `max_iters` |
| 无 `optimizer` 只静默跳过；`message_hub` 必存 | `runner.py:2078`；`runner.py:2234` 无条件写 |
| **`save_param_scheduler` 默认 True，不受 `save_optimizer=False` 影响** | `checkpoint_hook.py:135` |
| **`state_dict()` 存整个 `__dict__`（含 `end`/`last_step`），`load_state_dict()` 是 `__dict__.update()`** | `param_scheduler.py:140-152` |
| `step()` 只在 `begin <= _global_step < end` 时写 LR | `param_scheduler.py:210` |

合起来：直接 `--resume` 会把 `end=20000`、`_global_step=19999` 装回来，此后
LR 永不再被更新，**40k iter 在一个冻结的 LR 上跑完，且不报错、不崩**。

- `launch_h2_server.sh` 新增 `resume60k` 模式，预检后带三道闸：解析后配置必须含
  `max_iters=60000`/`lr=6.94e-5`/`end=40000`（致命）、日志必须出现

## 2026-09-30：H2 与 09-30 big fix 五臂的对照结论

对照条件：**同骨干 Swin-L、同 20k 预算、同 val 1000、同 seed 3407、同 512 裁剪、
同固定划分**，唯一差别是**解码器与损失**（H3 系 = 仓库 HyperSeg 解码 + 自定义损失；
H2 = Mask2Former 解码 + 匈牙利匹配损失）。指标语义一致，可直接并排。

### 有标注 val（原生分辨率，best 点）

| 臂 | 解码器 | 原生 val mIoU | 出现步 |
| --- | --- | ---: | ---: |
| bgfix `aug` | HyperSeg | **0.7042** | 20000 |
| bgfix `baseline` | HyperSeg | 0.7038 | 17000 |
| **H2** | **Mask2Former** | **0.6980** | **20000** |

| bgfix `loss` | HyperSeg + 假背景惩罚 | 0.6863 | 18000 |

**结论 1：等预算下 Mask2Former 解码没有追平仓库 HyperSeg 解码。**

H2 落在"纯 baseline 之下、惩罚臂之上"的中间位置。
注意 H2 的平台在 18000–20000 已稳定（69.79/69.42/69.80），**不是欠训造成的差距**；
但 20k 对 Mask2Former 这个解码器是否偏短，需要与同预算的 H3 臂同等看待 ——
两者预算相同、都跑满，所以这个比较是干净的。

**结论 2：H2 在"已经塌掉的那批图"上把背景吃回去的能力明显强于 HyperSeg 解码臂**
