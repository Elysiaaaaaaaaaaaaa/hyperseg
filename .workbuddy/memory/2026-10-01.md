关键事实与判据（已全部回写进 skill `docker-vhdx-compact`）：
- VM 内 `/dev/sdd`（挂载 `/mnt/docker-desktop-disk`，选项 **`rw,relatime`，无 discard**）
  `df` 只显示 Used 1.6 G：`isocache` 1.6G（ISO 缓存，常驻）+ `data` 4.3M + `lost+found` 16K。
  → **1.9–2.1 GB 就是压缩下限**，再压收益极小。
- **fstrim 判据**：第 1 遍 trim 101 MiB，**第 2/3 遍 `0 B trimmed`** → 空闲块此前已被 UNMAP
  ⇒ 不必重启 Docker 反复压，**一遍 compact 即可到底**（比 skill 里旧基线"第一遍只到 7.26 GB"更顺）。
  设备能力：`discard_max_bytes=4294966784`、`discard_granularity=1048576`。
- `wsl.exe` 仍被安全策略拦截；`docker pull alpine` 也**不可用**（VM 内到 registry-1.docker.io 超时），
  只能走静态 busybox + `docker import` + `nsenter -t 1 -m -u -n -i -r` 进 VM 这条路（宿主机 curl 通）。
- **本机 agent 会话不是管理员**（`net session` 判否）。`Start-Process cmd.exe -Verb RunAs`
  被安全策略**明确拦截**；`Start-Process diskpart.exe -Verb RunAs` 在沙箱内会**静默杀掉整个

  `Out-File` 到临时文件再用 Read 读回。这是本机 PowerShell 通道的硬限制。
- diskpart 脚本**别用 `printf` 生成**（Git Bash 会把 `\\` 吞成 `/`，写出 `D://docker//…`）；

**用 best 跑 `run_h2_ckpt_test.sh <ckpt> best132k`（脚本哈希 `901e78b8…` 与本地一致）**：

- `test.txt`（699 张有标注）= **mIoU 78.56** / aAcc 89.35 / mAcc 87.25，94 s、2020 MB。
  8 类 7 涨 1 降：唯一下降是 Barren（53.02 → 52.51），**但 Barren Acc 反升 +3.58**
  （63.87 → 67.45）⇒ 不是更保守，是"敢预测但边界不准"。
- `test_2` 1300 张整图导出 214 s（0.133 s/张），本地复核 **PASS**：
  全部颜色类型 0 / 位深 8 / 无 PLTE / 无 tRNS / 1024×1024 / 名称与输入逐一相同 /
  id 全在 1..8 且**没有 0**。内容 SHA-256 `0d71861156…6ad19bd5`（解压后 1300 张逐字节拼接）。

**必须记住的坑：MMSeg 导出的 id 是「原始标签空间」1..8。**
管线 `reduce_zero_label=True`，MMSeg 在导出时把 id 加回 1 ⇒ **1=Background，不是 0**；
出现 0 才是 ignore 泄漏。按 0..7 去解读预测会整体错一位。

**核心结论（与直觉相反）**：延长训练涨了分布内精度（82k 77.65 → 132k 78.56，+0.91），

（全部臂最高），h3 塌陷池（146 张）里 0.8274 → 0.8581。20k 臂那种"把背景吃回去"
的表现（池内 0.7321 / Building 0.2281）反而退回了。
⇒ **不能用 test.txt 的提升推断 test_2 变好**；无标注集的病是分布外覆盖
（训练先验背景仅 27.8%，模型在塌陷池里给到 86%），加迭代只会把训练先验拟合得更牢。

**test.txt 曲线补齐到 4 个测点**（服务器只剩 `best_mIoU_iter_132000.pth` 与 `iter_160000.pth`，

| 20k 臂 @20000 | 69.80 | 70.08 |
| 160k 臂 @82000 | 76.23 | 77.65 |
| 160k 臂 @132000（val best） | 78.20 | 78.56 |
| **160k 臂 @160000（末点）** | 78.09 | **79.44** |

**关键结论：`save_best='mIoU'` 选点在这一臂上是次优的 —— 末点 test.txt 79.44 比 best 的
78.56 高 +0.88**，因为 val 在 132k 后进平台（噪声 ±0.5，699 张）而 test 仍在上行。
末点唯一大改善类是 Barren（52.51→57.05，+4.54，Acc 67.75→77.76）。
test 全程 > val，无对 val 过拟合。

**新增工具** `experiment/mask2former_uav/analyze_image_stats_vs_perf.py`（纯 CPU，
逐图 6 个统计量：contrast_std/rms/p95p5、detail_lap、detail_hf、entropy）；
输出 `results/stats_{test2_vs_predbg,test_labeled,train_prior}.json`。
**注意：5598 张的 train 划分要跑 ~30 min，1300 张 test_2 要 ~17 min，别设太短的超时。**

**「预测差的图是低对比度/低分辨率」假设的检验结果（重要）：**

- **低细节这一半成立**：`detail_lap~背景占比`，有标注真值 ρ=−0.256（五分位真值背景
  0.383→0.194 单调），test_2 预测 ρ 最高到 **−0.494**（h2 best132k）。
- **低对比度这一半不成立**：`contrast_std` ρ 只有 −0.133，`contrast_rms` 甚至**反号**（+0.203）。
  ⇒ **不要拿"对比度"当自变量，要处理的是高频能量（细节尺度）。**
- **塌陷是断崖不是斜坡**：detail 最低五分位预测背景 0.719，第二分位骤降到 0.317（2.3×），
  而真值趋势在该区间是平滑的（0.383→0.292）⇒ 这部分是模型病理，非任务上限；
  且最低细节箱真值里**仍有 61.7% 是前景**。
- **越训越重**：Q1 上 20k 0.636 → 82k 0.676 → 132k 0.719 单调上行。

**「训练中随机降对比度/分辨率」这个实验项目里已经做过 = `h3_bgfix` 的 `aug` 臂**
（`bgfix_dataset.py`：zoom_out 真实降尺度 + **gsd 降采样再升采样** + 方向性偏色/雾化低对比/噪声 + GaussianBlur）。
20k 同种子结果：**原生 val +0.05pt、代理（0.5/0.625/0.75 降采样）均值 +0.06pt —— 噪声级**；
但 test_2 背景占比 0.3087→0.2992、`bg>0.8` 图数 122→101（唯一没引入新病理的臂）。
真正把 `bg>0.8` 打到 42/27 的是 **`false_background` 惩罚（决策层）**，代价域内 −1.12~−2.01pt。

**机制（写进 experiment.md 了的推理）**：真值里低细节 ⇔ 背景多（ρ=−0.256），
所以**无差别随机降质主要在合成「(低细节, 背景标签)」这个配对 —— 正是要拆的捷径**，
等于给捷径喂样本。要有效必须让**降质后的图仍带前景监督**（只对前景占比高的样本降质）。

**H2 管线现状**：`RandomResize(0.5–1.5)+RandomCrop(512)` 已有真实降尺度分支；
`PhotoMetricDistortion` 默认 `contrast_range=(0.5,1.5)` 已有 ±50% 对比度抖动；
**缺**模糊 / 雾化偏色 / 噪声 / down-up 重采样。优先级：决策层 > 选点（用末点） > 增强。

### 17:05–17:30 归因修正（重要，推翻上面"低细节是主因"的写法）

补跑两件事：
1. **训练集 5598 张分层先验**（`stats_train_prior.json`，跑了 42 min）：与真值侧几乎逐位一致
   —— `detail_lap~bg_frac` ρ=−0.265，五分位 0.391/0.293/0.269/0.230/0.205 平滑单调。
   **训练先验的 0.391→0.205 是平滑的，test_2 预测的 0.719→0.317 是断崖 ⇒ 断崖不在数据里。**
   且训练最低细节箱仍有 60.9% 前景 ⇒ **"没有低细节+前景样本"这个解释不成立**。
2. **`attribute_detail_vs_appearance.py`**（给 test_2 每张图补算逐通道均值/亮度/色偏）：
   - `detail_lap ~ cast_br(B−R)` = **−0.675**、`~mean_r` +0.623、`~lum` +0.578
     ⇒ **「低细节」与「暗 + 蓝绿偏色」几乎是同一个变量，不是两个独立现象。**
   - 偏相关：控住 cast_br/lum 后 detail_lap 仍 −0.266；控住 detail 后 cast_br 只剩 +0.141
     ⇒ **细节更直接，偏色主要靠交互起作用。**
   - **分层（先按蓝偏三档，档内按细节二分，预测背景占比）**：
     蓝偏低 0.305/0.205、蓝偏中 0.350/0.280、**蓝偏高 0.759/0.289**
     ⇒ **塌陷只发生在「高蓝偏 × 低细节」这一个格子**，单有其一都不触发
     （蓝偏高但细节丰富只有 0.289，完全正常）。**病因是交互。**
   - test_2 整体均值 R/G/B = 95.2/99.1/94.5 vs 训练 106.3/107.8/100.2（整体偏暗 + 略偏蓝绿）。

**由此修正的建议**：单独加"降分辨率"（gsd）是打空的一半，必须"压细节 + 改外观（雾化/曝光/偏色）"成套上；
`h3_bgfix` 的 aug 臂恰好是成套的，所以它是唯一方向正确的臂；
但它被 `eval_proxy.py` 低估了 —— **代理只扫细节轴，而病因是二维交互**，
以后复现这类实验必须构造「细节 × 色偏」二维代理网格。

**新增脚本**：`analyze_image_stats_vs_perf.py`（分层统计）、
`attribute_detail_vs_appearance.py`（归因判别）。**注意 `analyze_*` 跑 5598 张要 42 min、
1300 张要 17 min，别设短超时；`attribute_*` 只读图不跑 ndimage，3 min 即可。**
